## What was done

### 1. UX-01 remaining: replace hardcoded `#ffff00` search-highlight color

**Before:** `.search-highlight` in `App.css` used:
```css
background-color: var(--accent-yellow, #ffff00);
color: var(--text-on-accent, var(--text, #000));
```
Neither `--accent-yellow` nor `--text-on-accent` were ever defined in `theme.css`,
so the highlight always fell back to pure `#ffff00` with `#000` text — jarring on
both light and dark surfaces, and disconnected from the theme system.

**After:** Added `--color-highlight` and `--color-highlight-text` tokens to `theme.css`
(light: `#f5d678` bg / `#25231f` text; dark: `#e8c96a` bg / `#25231f` text), and
updated `.search-highlight` in `App.css` to use them.

### 2. Harden `MarkdownPreview.tsx` highlight injection

`highlightSearchMatches` was injecting the raw matched text into the span's HTML
without escaping. The query is user input from a search box; a query containing
`&`, `<`, or `>` would be misinterpreted as HTML when the browser re-parsed the
injected span innerHTML. Fixed by re-escaping the match before injection.

### 3. Regression tests added (`MarkdownPreview.test.tsx`)

- Entity-splitting: query "amp" against source "AT&T reported" must not split the `&amp;` entity
- Lone `&` query: "Bed & Breakfast" with query "&" — no highlight (entity-split protection), DOM text correct
- Adjacent term: "AT&T reported record profit" with query "report" — highlights "report" only, "AT&T" text intact
- Angle-bracket query: `<tag>` query does not create a DOM element from the query string
