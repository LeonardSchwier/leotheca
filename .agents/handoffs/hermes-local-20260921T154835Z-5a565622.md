## Task
UX-01 spec 13.5: "The view selector uses text labels at Wide and Expanded widths."

## What was done
The `SegmentedControl` primitive rendered either an icon OR a label per option,
never both. `DocumentHeader.tsx` passed `icon` + `label` for each view-mode
option, so only the icon was visible — no text label at any width.

Changes:
1. **`src/ui/SegmentedControl.tsx`** — when both `icon` and `label` are set,
   render both: `<Icon>` as a leading glyph and `<span>{label}</span>` as
   visible text. Updated the `SegmentedControlOption` interface doc to
   reflect the icon+label variant.

2. **`src/app/layout/DocumentHeader.tsx`** — pass
   `className="document-header-viewmode"` to the `SegmentedControl` so the
   call site can narrow the primitive's generic 30px icon-slot min-width
   to 0 (the label is now the width driver, not the icon).

3. **`src/app/App.css`** — added
   `.document-header-viewmode .segmented-option { min-width: 0; }`
   scoped to this call site only.

4. **`src/app/layout/DocumentHeader.test.tsx`** — regression test asserting
   all three options (Source/Split/Preview) show their text labels via
   `getByRole("radio", { name })` and each still carries its `data-icon`
   attribute.

   label are visible, `aria-label={option.label}` is redundant (the `<span>`

   unchanged; the label adds width but the icon size is appropriate for

   active" test uses `getByRole("radio", { name: "Source" })` — this still
   works because the radio button's accessible name comes from its
   `aria-label` (which is `option.label`), not from the `<span>` text.
   The new test verifies the `<span>` text is present independently.
