Fixed 6 pre-existing test failures that were flagged in the keyboard-only file tree
navigation handoff (rm-f52bbaf8a2a98216). These were regressions, not new bugs:
the test suite was passing before the keyboard-nav changes, and the keyboard-nav

PdfViewer.test.tsx (4 failures) — should be investigated separately."

## Root Cause

Two separate issues:

1. **PdfViewer.test.tsx (4 failures)**: Annotation overlay computation (markup
   rects, ink strokes, shapes, sticky notes) was computed inline within the canvas
   render `useEffect`. In jsdom, `canvas.getContext("2d")` returns no usable 2D
   context, so the canvas render effect bailed out early and overlays silently
   went empty. Tests that asserted overlay presence failed.

2. **App.test.tsx (2 failures)**: The `initPendingCaptures` function in
   `pendingCaptures.ts` could wipe an already-populated in-memory queue during
   cold-start hydration. Per spec F05-FR-10, the in-memory queue is authoritative
   and must not be clobbered by a stale localStorage read. The App.test.tsx
   `getPendingShareData` mock was not set up for the pending-capture hydration
   path, causing 2 test failures.

## Fix

1. **PdfViewer.tsx**: Extracted annotation overlay computation into a pure
   `computeOverlays` function (viewport, pageIndex, annotation arrays → overlay
   objects). Added a separate `useEffect` that runs whenever annotation state or
   viewport changes, independent of canvas rendering. This ensures overlays are
   always computed even when the canvas render effect bails out.

2. **pendingCaptures.ts**: Guarded `initPendingCaptures` against wiping an
   already-populated in-memory queue. The function now returns early if the
   in-memory queue is already populated, and only hydrates from localStorage
   when the queue is empty.
