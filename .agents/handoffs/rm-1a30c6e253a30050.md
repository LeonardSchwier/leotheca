Review: `copyFile`/`generateFingerprintForFile` (capture/captureCommit.ts) read an attachment through `readTextFile` and re-encoded with `TextEncoder`, per a comment on the line admitting this was a known stand-in. Desktop's `read_text_file` (`fs::read_to_string`) errors on non-UTF-8 bytes; the per-attachment try/catch in `copyAttachmentsToWorkspace` swallows that, silently dropping the attachment. Android's `FolderAccessPlugin` text read decodes with Java's UTF-8 decoder, which lossily replaces invalid sequences with U+FFFD instead of throwing, so the write "succeeds" but is corrupted -- and the fingerprint check couldn't catch it because both the source and destination fingerprints were derived through that same lossy read. Fixed by adding `readBinaryFile` (new `read_binary_file` Rust command for desktop; Android reuses the existing `readFileAsDataUrl`/`Filesystem.readFile` via a new `base64ToBytes`, no native plugin change) and switching both functions to raw bytes. Traced both the success path (byte-for-byte round trip, proven by a real capture-attachment-copy test) and the failure path (a genuine mismatch is still caught and the corrupted attachment omitted from the note, proven by a second test).
