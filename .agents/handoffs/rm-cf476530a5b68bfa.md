## The defect

`read_text_file`/`read_binary_file` (`src-tauri/src/commands.rs`) call `check_unscoped_path_allowed`, which accepts only a path inside the active workspace root or the app config directory, rejecting everything else -- confirmed by that module's own existing test `check_unscoped_path_allowed_rejects_a_target_outside_both_roots`. Both triggers of the external-open feature handed the frontend a bare external path (`App.tsx`'s `handleExternalFileOpen`, `tauriBridgeImpl.ts`'s `pickMarkdownFileToOpen`) and fetched its content via `readTextFile(path)` -> the gated `read_text_file` command. For a genuinely external file -- by this feature's entire purpose, outside both allowed roots -- that call always failed, caught by `handleExternalFileOpen`'s own `catch { return; }` and silently discarded. The read-only "Open file from outside the vault" scratch view (`ExternalFileView.tsx`) could therefore never actually show a real external file's content on any of its three delivery paths (OS file-association cold start, live relaunch/macOS `RunEvent::Opened`, in-app picker). This was invisible in the existing frontend test suite because `App.test.tsx`/`tauriBridgeImpl.test.ts` mock `readTextFile` entirely (`vi.fn` resolving whatever `mockResolvedValueOnce` sets), so the tests never exercised the real Rust containment check the feature's own correctness depends on.

## The fix

Rather than relaxing `read_text_file`/`read_binary_file` (shared by many other, still-workspace-scoped callers) or adding a second, separately-reachable unscoped-read command a compromised webview could invoke directly with an arbitrary path (the exact anti-pattern `skills/change-quality-gates.md` warns against), the read now happens inside the same trusted Rust call that already establishes the external path's provenance -- mirroring `export_text_file_via_dialog`'s own already-reviewed guarantee for the write side ("the destination there is never a value a webview can supply in the first place").

- New `src-tauri/src/external_open.rs`: `ExternalMarkdownFile { path, content }` and `read_markdown_file` (plain `fs::read_to_string`, deliberately no containment check -- see its doc comment for why that is correct here).
- `PendingOpenFile` (cold start) and the `open-external-file` event (live relaunch / macOS `RunEvent::Opened`) now carry the already-read file instead of a bare path; `lib.rs` reads the file immediately after `extract_markdown_path`/`markdown_path_from_urls` succeeds, before buffering/emitting.
- New `pick_and_read_external_markdown_file` Tauri command shows the native "Open File" dialog and reads the pick in the same Rust call, replacing the frontend's own direct `@tauri-apps/plugin-dialog` `open()` call.
- `tauriBridgeImpl.ts`: `takePendingExternalFile`/`onExternalFileOpen`/`pickMarkdownFileToOpen` updated to the new `ExternalMarkdownFile | null` contract; `tauriBridge.ts` re-exports the type. `capacitorBridgeImpl.ts`'s Android no-op stubs updated to the same return shape for contract parity (still unused -- `tauriBridge.ts` re-exports the Desktop implementation directly for these two functions, not a platform dispatch).
- `App.tsx`'s `handleExternalFileOpen` now takes the whole `ExternalMarkdownFile`; an in-workspace target is unaffected (still reads fresh via the ordinary `handleOpenFile` -> `readTextFile` path, which stays correctly contained); an outside-workspace target uses the delivered `content` directly, with no second gated call.

`check_unscoped_path_allowed` and every other caller of `read_text_file`/`read_binary_file` are untouched, so the 2026-09-22 containment hardening for ordinary workspace reads is unaffected by this fix.
