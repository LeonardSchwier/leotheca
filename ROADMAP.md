# Roadmap

Leotheca ships in waves: coherent, demoable slices rather than a fixed calendar schedule. A wave ships when its feature list is done and stable. Waves build on each other, a later wave does not start until the previous one is in a usable state.

| Wave | Theme | Target platforms | Status |
|------|-------|-------------------|--------|
| v1 | Core viewer and editor | Linux desktop, Android | In progress |
| v2 | Knowledge navigation (links, search, graph) and inline live-preview editing | Linux desktop, Android | In progress, pulled forward alongside v1; live-preview moved here from v1 |
| v3 | Compatibility layer foundations (community plugin API shim) | Linux desktop | Not started, deferred |
| v4 | Mobile parity and polish | Android | In progress, pulled forward alongside v1 |
| v5 | Extensibility ecosystem (themes, snippets, templates) | Both | Not started |
| v6+ | Additional platforms (macOS, Windows), publishing, import/export ecosystem | TBD | Not started |

Sync is intentionally absent from this table. Leotheca does not build or bundle a hosted sync product, see the README's Sync section.

## v1: Core viewer and editor

Goal: a single window application that opens a local folder of markdown files and lets someone comfortably read and write notes in it, with an editing experience that feels as good as a dedicated writing tool.

**Definition of done:** install the Linux build and the Android build, point each at the same folder of markdown files (shared via whatever folder-sync mechanism the user already uses), and comfortably read and write notes on both, with an editing experience that feels considered and fast.

### Shipped so far

- 🗂️ **Local Folder Workspace** — file tree (browse, create, rename, delete, right-click context menu), tabs (rename via right-click too) with autosave, remembers the last opened workspace and reopens the tabs that were open at the end of the last session. Ctrl+N creates a new note instantly in the current folder.
- 🔍 **Full-Text Search** — matches by file name first, falls back to note content.
- 📖 **Markdown Help** — a markdown formatting quick-reference popup.
- ✍️ **Editor** — CodeMirror 6 source-mode editing with markdown syntax highlighting, a separate rendered Preview mode, and a Split view. True inline live-preview editing (formatting rendered in place while typing, not a separate mode) is deferred to v2, see "Beyond v1" below — v1 ships with Source/Split/Preview instead.
- 🔗 **Wikilinks** — the common markdown syntax set, plus `[[wikilink]]` links: resolved by filename, clickable in Preview, autocomplete while typing `[[`.
- 🕸️ **Graph View & Backlinks** — a backlinks panel and a pannable, zoomable graph view of the whole workspace. By default the graph only shows notes with at least one incoming or outgoing wikilink — a "Show all notes" checkbox in the graph's header brings isolated notes back, since on a real large vault most notes have no links at all and showing every one of them as an unconnected circle with its full filename buried the actual link structure in noise.
- ⭐ **Bookmarks** — a panel for saving shortcuts to specific files or searches.
- 🎛️ **Command Palette** — Ctrl+K for quick access to core actions.
- ⌨️ **Keyboard Shortcuts** — Ctrl+N (new note), Ctrl+K (command palette), Ctrl+W (close current tab), Ctrl+Tab / Ctrl+Shift+Tab (cycle tabs), Ctrl+S (flush the current tab's autosave immediately), Ctrl+, (open Settings) — all listed in both the Settings panel and the "?" help dialog, not just discoverable by trial.
- 📸 **README Screenshots** — real screenshots (split view, graph view, settings), replacing the "coming soon" placeholder.
- ⚡ **Faster Re-Indexing** — an mtime-based cache (`.leotheca/link-index-cache.json`) so rebuilding the wikilink index skips re-reading a note's content when its mtime hasn't changed — a real win for same-session re-indexing (e.g. reopening the graph view without restarting the app). The directory walk itself isn't cached by this, so it doesn't meaningfully speed up cold app starts; see the v2 backlog below for that larger piece.
- ⚙️ **Settings** — theme (Follow System / Light / Dark), font size, whole-UI zoom, default view mode, workspace statistics, license viewer, resizable/collapsible sidebar.
- 🗑️ **Delete Behavior** — configurable per workspace: move to a project `.trash` folder (default) or delete permanently.
- 🐧 **Linux Packaging** — runs via Tauri, packaged as both AppImage and Flatpak.
- 📱 **Android Folder Access** — real folder access via the Storage Access Framework (point it at any folder, including one synced by an external tool), minimum API 29 (Android 10).
- ✅ **CI/CD** — CI builds and tests both the Linux and Android targets on every pull request. A tag push builds a Linux AppImage, a Flatpak bundle, and an Android APK and attaches all three to a draft GitHub Release (the Flatpak job is unverified until the first real run, the Android APK is debug-signed by design, see "Explicitly out of scope for v1" below).

Root-caused by regenerating from a fresh GitHub checkout of the same tool (`flatpak/flatpak-builder-tools`) instead of the pip-installed copy, which produced all 560 real sources correctly — see `flatpak/README.md`'s "Known issue" note for the full story and the corrected regeneration command. That fix alone wasn't enough: the re-cut tag's CI run hit the *exact same* `ENOTCACHED` error on `eslint` again, despite `node-sources.json` now genuinely containing its tarball. First guessed this meant switching `npm ci --offline` to `npm install --offline` (matching the tool's own reference example manifests) — **that guess was wrong**, confirmed by testing it via the new `workflow_dispatch` trigger below: the exact same failure recurred a third time. Actually root-caused by reading `flatpak_node_generator/providers/npm.py` directly rather than pattern-matching off an example: `node-sources.json`'s 603 "inline" cache-index entries each cover one *tarball* fetch, none cover the *separate* bare package-metadata registry lookup (`registry.npmjs.org/eslint`, no version) that `npm install` needs for its own semver-range re-resolution but `npm ci` never performs at all, since `npm ci` trusts `package-lock.json`'s already-resolved versions unconditionally. `npm install` re-resolving from `package.json`'s ranges is exactly what triggered the registry query in the first place, and this project's `eslint` peer-dependency conflicts (visible as `ERESOLVE` warnings in any real `npm install` run) are exactly the kind of situation that forces that query for real. Reverted to `npm ci --offline`, expecting that to be the real fix — **also wrong**, tested via `workflow_dispatch` a third time and hit the *exact same* `ENOTCACHED registry.npmjs.org/eslint` failure, disproving the theory that `npm ci` never queries the registry for peer-conflict resolution (it apparently does, at least for `eslint`'s specific `ERESOLVE` situation here, contrary to the npm documentation this theory was based on).

🚧 **Genuinely unresolved as of session 57's end**, deliberately stopped here rather than keep guessing: three plausible-sounding, individually-tested-and-disproven theories in a row (missing tarball entries; `npm ci` vs `npm install` cache-lookup differences; registry-metadata-index coverage) is a sign the actual mechanism isn't understood yet, not that the next guess will be the one. **The concrete next diagnostic step, not yet taken**: add a temporary build-command *before* the npm install line that dumps real ground truth from inside the sandbox — `npm config get cache`, `find "$npm_config_cache" -maxdepth 4`, `ls -la "$npm_config_cache/_cacache/index-v5"` (or wherever it actually resolves) — since every attempt so far has reasoned about the cache from the *generator's* source code and the *manifest's* env vars, never actually looked at what's really on disk at the moment `npm ci` fails. That would show definitively whether the index entries are even landing where npm expects them, or something more basic (a path/env-var mismatch, an extraction step not running) is wrong. Also worth trying directly: `npm config get registry` and checking whether `--offline` combined with an explicit `--prefer-offline`/`--no-audit`/`--no-fund` changes behavior, since npm's audit/funding checks sometimes issue their own uncached registry requests unrelated to dependency resolution at all — genuinely not yet ruled out. Whoever picks this up next (a fresh session, or the daily automated routine, see `CONSTITUTION.md`) should start from that diagnostic, not from a fourth theory.

Also added `workflow_dispatch` to `release.yml` (gated so only a real tag push can reach the `publish` job) so this kind of iteration doesn't need a delete-and-recreate tag cycle each time — used it for exactly that purpose across this whole investigation. All three real bugs found so far only became visible because the CI job is a *real* build, not a syntax check — exactly the point of treating it as the actual verification path instead of trusting the manifest and generated sources (or a plausible-looking fix) on inspection alone. The `v1.0.0` tag itself was not re-cut after this third failure — it still points at the `npm install --offline` commit, one fix behind current `main`. Re-cut it once the Flatpak job is actually green, not before.

Implemented as a CodeMirror 6 decoration layer (`src/editor/livePreview.ts`) built from the markdown syntax tree, not a separate view mode, Split and Preview are unaffected. 11 new tests, live-verified visually (cursor-on-line vs. cursor-away screenshots). Detected with a regex pass over the document text (the standard markdown syntax tree has no `[[ ]]` node), skipping any match that falls inside an inline code span or code block so `` `[[not a link]]` `` stays literal text. Markup reappears while the cursor is on that line, same interaction as the other live-preview elements. 5 new tests in `src/editor/livePreview.test.ts`. Lists were still not covered as of this entry, since fixed below; the whole-document (not viewport-scoped) recompute noted in session 56 is also still unaddressed.
  - ✅ **Inline Live-Preview Bullet Lists (session 58)**: a `BulletList`'s `-`/`*`/`+` marker (plus the space after it) is now replaced with a rendered bullet dot ("• ") in Source mode when the cursor isn't on that line, the same interaction as the rest of live-preview, closing out the "lists" follow-up noted above. Implemented as a CodeMirror `WidgetType` (`BulletWidget` in `src/editor/livePreview.ts`) rather than plain hiding, so the line still visually reads as a list item instead of losing its marker outright; all three bullet characters render identically. Deliberately does not touch `OrderedList` markers ("1.", "2.", ...): the number is meaningful content the reader needs, not pure decoration the way a heading's `#` is, so it stays exactly as typed. 5 new tests, covering nested lists and the ordered-list no-op case. The whole-document recompute from session 56 is still the one remaining open item for this feature.
- 🧩 **v3 — Compatibility Layer** — reading a community plugin manifest format so existing plugins from the wider note-taking ecosystem can run against Leotheca, without ever naming that ecosystem's original application (see `CONSTITUTION.md`). Not started.

- 🎨 **v5 — Extensibility** — themes, snippets, templates. Not started.
- 🚚 **Moved From v1** (maintainer decision, session 55):
  - 🚶 **Directory Walk Caching** — `rebuildLinkIndex` and `getWorkspaceStats` still walk every folder on every call (confirmed ~83s alone for 514 `listDir` calls on the maintainer's real 580-note vault) — the mtime-based content cache shipped in v1 doesn't touch this. Would need a persisted directory-listing snapshot or filesystem-watch-based invalidation, a materially larger cross-cutting design (Rust, Android Java, two TypeScript call sites).
  - 🔁 **Symlink Cycle Handling** — a symlink cycle inside a workspace folder (a directory symlinked back to one of its own ancestors) would cause infinite recursion in every recursive directory walk (`workspace_stats` in `commands.rs`, `expandAll`/`runSearch` in `fileTreeStore.ts`) — none track visited canonical paths, and `list_dir` follows symlinks. Requires a user to have manually symlinked a directory into their own vault pointing back at an ancestor; no sync tool does this on its own. Fixing it means adding visited-path tracking to three separate recursive walks for a self-inflicted, low-likelihood edge case.

Ships with its own Settings toggle ("Frontmatter aliases", on by default per the opt-out policy this backlog's intro links to); disabling it falls back to file-name-only resolution exactly as before this session. An absolute URL or `data:` URI is left untouched, both already covered by existing behavior (CSP blocks a remote image from loading at all, per "Offline by design"; a `data:` URI already renders natively). New binary-file-write plumbing was needed on both platforms since none existed: a Rust `write_binary_file` command (`src-tauri/src/commands.rs`, bytes over Tauri IPC as a plain number array, no new Cargo dependency) and a `writeBinaryFile` method on the Android `FolderAccessPlugin` (bytes cross the Capacitor bridge as base64, decoded with the platform's own `Base64` class; refactored a `resolveOrCreateTargetUri` helper out of `writeTextFile` so the new method didn't duplicate that URI-resolution logic).   - ✅ **Custom fields (session 59)**: a "Properties" panel above the editor shows every top-level frontmatter field (scalar or flat list) as an editable label/value row, with add and remove, backed by a new `parseFrontmatterFields`/`applyFrontmatterFields` pair in `src/linking/frontmatter.ts` that generalizes the existing hand-rolled aliases parser rather than pulling in a YAML library (per `CONSTITUTION.md`'s dependency-hygiene rule; nothing in this app's UI needs nested YAML values, so that gap was left deliberately, not overlooked). Deliberately not a type-specific editor (no date picker, no checkbox, no per-type dropdown the way the wider note-taking ecosystem's own Properties view has): every value round-trips as a string or a flat, always-double-quoted list of strings, an honest, safe trade-off over hand-replicating YAML's full scalar-quoting rules. Content the parser doesn't understand (a nested map, a comment) is never partially parsed or dropped, it is preserved verbatim and re-emitted untouched whenever a *different* field is edited through the panel, so the panel can never silently destroy frontmatter data it doesn't display. Editing a field mid-note (with the cursor elsewhere in the body) required new plumbing in `MarkdownEditor.tsx`: the CodeMirror view previously only ever synced from an external `value` change on file switch, so a new effect now diffs old and new content (`src/editor/textDiff.ts`'s `minimalChange`, a prefix/suffix trim) and dispatches only the actually-changed range, keeping the user's cursor and scroll position stable instead of jumping on every properties edit. A new "Colors" toggle opens a small panel for defining color groups (`WorkspaceSettings.graphColorGroups`, new per-workspace setting, default empty): each group is a text query plus a color swatch, matched in the same case-insensitive-substring way as the filter box, first matching group in the list wins so a group's position is its priority, and a node that matches nothing keeps the graph's existing default color. Deliberately no reordering UI beyond add/remove; simple enough to skip for a first pass, priority is still whatever order groups were added in. No settings toggle needed for this one, unlike other items in this backlog: an empty `graphColorGroups` array (the default) leaves the graph looking exactly as it did before this feature existed, so there's nothing to opt out of until a user actually defines a group. `computeVisibleGraph` (`src/graph/GraphView.tsx`) was pulled out as the single function both the canvas layout pass and the render-time empty-state/node-count logic now call, so the two can't drift on what counts as "visible" now that mode, showAll, and the filter all interact. 24 new tests across `GraphView.test.tsx` and `workspaceSettings.test.ts`.
- 🏷️ **Tags** — as Market Solution #2 does them: `#tag` syntax, a tag list/pane, nesting.
- 🔎 **Advanced Full-Text Search** — a query syntax, as Market Solution #2's search has: path/tag filters and operators, not just the current plain-substring, filename-first-then-content-fallback search.

Very late in this backlog, lower priority than everything above:

- 🌐 **Web Clipper** — a browser extension, as both Market Solution #1 and Market Solution #2 ship. Not on any earlier version of this roadmap at all until now.
- 🖱️ **Scroll-to-Zoom** — zoom/font-size controls that more closely match Market Solution #2's actual interaction model (e.g. Ctrl+scroll or Ctrl+Plus/Minus to zoom on the fly), not just the Settings-panel-only numeric fields Leotheca has today for font size and whole-UI zoom.
- 🖼️ **Whiteboards / Canvas** (queued 2026-08-28 by the daily competitor changelog scan, Joplin 3.7): an infinite, pannable, zoomable canvas view for arranging notes, images, PDFs and cards spatially, connected with labelled arrows, rather than editing prose top-to-bottom. Fits well: it is stored as the open JSONCanvas format inside an ordinary note's fenced code block, not a proprietary database, so it needs no new file format of its own (JSONCanvas is also the format behind Market Solution #2's own Canvas feature), stays fully client-side with no network call, and is genuinely a new feature (not a bug fix).
- 🔗 **x-callback-url Automation Commands** (queued 2026-08-28 by the daily competitor changelog scan, Joplin 3.7.10): `getCurrentNote` and `createNote` commands via the x-callback-url convention already used by other inter-app automation tools (Hookmark and similar), letting an external app read or create notes through an OS-level custom URL scheme. Fits well: adopts an established cross-app convention instead of inventing a bespoke one, and is purely local URL routing handled on-device, no network call involved.
- 🔒 **Note Lock (per-note password encryption)** (queued 2026-08-28 by the daily competitor changelog scan, Joplin 3.7.8-3.7.12): password-locking an individual note so it displays encrypted and inert (title and body uneditable) until unlocked for the current session, rather than encrypting an entire workspace. **Needs the maintainer's own explicit sign-off before implementation**, per `CONSTITUTION.md`'s "High-risk feature categories" (encryption/cryptography gets queued, never auto-implemented or design-judged by this scan).
