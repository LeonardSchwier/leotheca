It's also genuinely lower-stakes than the other three: a bad cache entry just triggers a real re-read, no data loss, unlike a workspace setting or a bookmark, which have no other copy anywhere.

For the three files actually in scope, built one shared primitive library first (`settings/decode.ts`): each decoder takes a raw value and a fallback, returns `{ value, corrupt }`, and treats "missing" and "present and valid" both as `corrupt: false` (an older or hand-trimmed file is not corruption) while "present but wrong type/enum/range" is `corrupt: true`. This mattered for `workspaceSettings.ts` specifically, which has 18 fields: writing one bespoke check per field would have been both more code and more opportunity to get one of them subtly wrong; the shared primitives made applying real validation to all 18 mechanical instead of a fresh design problem each time.

`decodeWorkspaceSettings` overlays validated fields on top of the raw parsed record (spread first, known fields second) rather than reconstructing the object field-by-field, which is what makes an unknown top-level field (a newer app version's own setting this build doesn't recognize) survive a load/save round trip instead of being silently deleted — proved directly with a fixture asserting the unknown key is still there after decode. The same trick handles an unrecognized `version`: flagged as corrupt, but its actual value is left alone rather than forced to `1`, so a genuinely newer file's version marker isn't downgraded by an older build that happens to load it once.

`lastOpenPaths`/`lastActivePath` needed the workspace root to validate against (an absolute path is only "valid" if it's actually inside this workspace), which is exactly the same lexical containment question F-004's `resolvePathWithinWorkspace` already answers for note-relative links — added a sibling `isPathWithinWorkspace(root, absolutePath)` to `workspace/paths.ts` reusing its existing private helpers, rather than inventing a second containment check. `attachmentsFolder`/`templatesFolder` get their own `decodeRelativeFolder`, rejecting absolute or `..`-containing values the same way.

**The actual "never silently overwritten" guarantee lives in the store layer, not the decoder.** `decodeWorkspaceSettings` is pure and does no I/O; `settings/store.ts` is what decides whether to persist anything, and it doesn't, on a corrupt load. Added a `workspaceSettingsCorrupted` signal, set alongside `workspaceSettings.value` in both `initSettings` and `setWorkspacePath`, and a new `repairWorkspaceSettingsFile` that only writes when explicitly called (wired to a new "Rewrite settings file" button in `SettingsPanel`, next to the existing save-error/retry row it's modeled on). Proved this two ways rather than one: a store-level test that a corrupt `setWorkspacePath` load leaves zero `writeWorkspaceTextFile` calls, and a component-level test that the button actually appears and actually calls the repair function when clicked.

Bookmarks and global config got the same per-field/per-entry validation (`decodeBookmarks` drops an individually malformed array entry while keeping the rest — a bookmark missing its own `id` would otherwise have silently broken `removeBookmark`'s `id` match) but no dedicated recovery UI: checked first that neither is ever auto-saved merely by loading (only an explicit bookmark add/remove, or opening a workspace/changing the theme, ever calls their respective saves), so the destructive-auto-overwrite risk the UI exists to prevent doesn't apply to them the same way.

**The resolver** (`commands.rs`'s `resolve_within_workspace`): rejects an absolute or `..`-containing workspace-relative path before any filesystem access, then canonicalizes the target (or its nearest existing ancestor, for a not-yet-created nested path, via a new `nearest_existing_ancestor` helper) and requires the canonical result to sit inside the canonicalized workspace root, checked component-wise (`Path::starts_with`) rather than by string prefix specifically to avoid the classic `/vault` vs `/vault-evil` false-accept. A symlink anywhere in that resolution, including the exact target itself, is only followed if its real location resolves inside the workspace; a dangling symlink sitting exactly at the target is rejected too (it has no canonical form, and would otherwise look like "doesn't exist yet" to a naive existence check and slip through). 22 new Rust tests exercise this directly with real temp directories and real symlinks (`#[cfg(unix)]`), including the exact bug shapes the audit item worried about.

A trailing separator asserts "this must be a directory" at the OS level, so `fs::rename`/`fs::remove_file` on an ordinary file then fails with `ENOTDIR`. Found because the *existing* `trash_path` tests (unrelated to this change on their face) went red the first time the full suite ran, not because a new test was specifically written to catch it, a good reminder that running the whole existing suite after a change, not just the new tests, is what actually catches this class of regression.

## 2026-08-30 — OpenCode (qwen3.6-35b-a3b), F-005 search memory guard — `isTextFile` whitelist, batch size pre-add flush, conservative unknown-size default

The CODEBASE_AUDIT.md (F-005) found three gaps in the search content-read batching that survived the layer-3 OOM fix (which bounded batches by byte size but didn't address these):

1. **Non-text binary files sent through native string serialization** — `isImagePath` only filtered images. PDFs, videos, archives, executables all had their content read via `readTextFilesBatch`, which on Android replaces invalid UTF-8 with replacement characters (`ByteArrayOutputStream.toString("UTF-8")`) instead of rejecting them, producing garbage search results; on Rust the file was read but wasted IPC/memory on content never meant to be searched. **Fix**: added `isTextFile(path)` in `types.ts` with a conservative whitelist of text extensions (md, txt, html, json, code files, config files, log, csv, YAML, TOML, etc.). Non-whitelisted extensions are treated like images — matchable by name but never content-read.

2. **Batch size check allowed one file to overshoot** — the old order (`pendingBytes += size; if (pendingBytes >= cap) flush()`) added the file's size *then* checked, allowing one batch to temporarily exceed the 8 MiB limit. **Fix**: changed to check `pendingBytes > 0 && pendingBytes + size >= cap` *before* adding, then add and schedule flush. Ensures no batch can grow unboundedly.

3. **Unknown file sizes defaulted to 0** — when the native walk doesn't report `size`, `entry.size` was `?? 0`, letting an unknown-sized file blend into a zero-size batch and defeat the byte cap entirely. **Fix**: added `CONSERVATIVE_UNKNOWN_SIZE = 4 MB`. When size is unknown, the batch assumes 4 MB so one batch can never hold more than two unknown-size entries before flushing.
