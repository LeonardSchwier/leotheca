# Historical decisions

This is an archive, not an agent entrypoint. Read `../CONSTITUTION.md` for current policy. The 2026-09-06 autonomous-pipeline decision there supersedes every older workflow, commit-permission, CI, claim-expiry, review, and session-log instruction below. Product and architecture history remains useful context. Old schedule descriptions are historical records, not proof that any runner is currently active.


## Current workflow decision

- 2026-09-06: The owner authorized multiple simultaneous autonomous workers, direct main commits without human review/merging, self-resolution of ordinary blockers, limited-CI fallbacks, recovery from dead sessions, and historic bug/documentation reviews after eligible feature work is exhausted. The current constitution and runbooks implement that instruction using expiring tokenized leases, isolated control transactions, durable per-task handoffs, evidence-based verification, and a tested ledger helper. Identity/timing settings are top-level variables. This supersedes all older operational workflow rules in this archive. Ledger/handoff-only pushes no longer rebuild/release unchanged application code; their roadmap state is covered by the policy workflow.

- 2026-08-27: The maintainer, live, asked why no releases were visible on GitHub and expected freshly built artifacts after every push, not only after a deliberate version tag. Resolved by adding a second release channel to `.github/workflows/release.yml`, rather than replacing the existing one: every push to `main` (in addition to the existing `v*` tag trigger) now also rebuilds all three artifacts and republishes them to a single rolling, always-recreated **`dev-build`** GitHub prerelease. The existing tag-triggered versioned release (draft, semantic-versioned, `CHANGELOG.md`-backed) is unchanged. See the updated "Versioning and releases" bullet above for why this had to be a prerelease specifically (Obtainium and F-Droid only track non-prerelease releases by default) rather than a change to the existing release's behavior. Checking the actual GitHub Actions run history the same day found this new channel was silently never publishing anything: `publish` required `flatpak` to succeed too, and `flatpak` fails on every run due to the pre-existing, already-documented npm-cache bug (see `ROADMAP.md`'s "Still open for v1"). Fixed the same day: `publish` now only requires `linux` and `android` to succeed, tolerates `flatpak` failing, and the release body says plainly when the Flatpak bundle was left out for that reason.
- 2026-08-27: The maintainer asked for `CONSTITUTION.md` to proactively address the specific, documented reasons agentic/"vibe" coding is reported to fail for real production software, not just to keep writing good code and hope. Added a new "Guardrails against known agentic-AI failure modes" section (after "Engineering practices"), informed by external research on AI-generated-code security vulnerability rates, "reward hacking" (gaming tests instead of fixing the underlying problem), the "80% problem" (non-functional requirements silently dropped), agentic entropy/architecture drift, hallucinated APIs and dependencies ("slopsquatting"), prompt injection via fetched external content, agent sycophancy, and overconfident/premature "done" claims. Each rule in that section is paired with the specific documented failure mode it counters, rather than stated as generic caution, so a future session understands why it exists.

- 2026-08-28: A different session picking up the next roadmap item independently discovered a real correctness bug in Advanced Full-Text Search's `-exclude` filter, shipped the same day by the daily automated routine despite a full green verification suite and 33 passing tests. Root cause and the new standing rule this prompted are recorded in "Guardrails against known agentic-AI failure modes" above (the "performance shortcut" bullet); the bug itself is fixed (same commit that added the rule). The maintainer, live, asked whether this meant other past commits needed the same scrutiny; the recommendation given (see that session's chat, not reproduced here) was a targeted, risk-based spot review of specifically the shipped features sharing this bug's risk shape (a cache, memoization, lazy evaluation, negation, or other order-dependent state deciding whether to skip work), not a full line-by-line re-audit of every prior commit, left for the maintainer to decide whether and when to commission.

- 2026-08-28: The maintainer, live, added speed of use (app startup, folder-open, and navigation time, including for large folders) as a standing engineering principle, with an explicit constraint on how to get there: no file-content caching, since the workspace folder is expected to be synced in the background by the user's own external tool and a stale cache can diverge from what that sync just wrote. See the new "Speed of use" bullet under "Maintainability and general engineering principles" above. Any performance change should be A/B tested against the current behavior as a baseline, not assumed to help.

- 2026-08-28: Technical documentation now lives in `documentation/`, with `documentation/ARCHITECTURE.md` as the canonical architecture map. It must stay synchronized with structural changes and guide engineers to the relevant subsystem and collaborators without requiring a full-codebase reading.

- 2026-08-28: Supersedes the routine's earlier direct-to-`main`, no-PR implementation policy whenever parallel coding sessions are possible. Codex, Claude Code, and every other session now coordinate through one repository-visible `ROADMAP.md` claim ledger, one claimed `agent/*` branch per item, pull requests, and an agent-owned integration pass at the start of every autonomous run. A claim-only commit on remote `main` is the mutual-exclusion lock, and the running agent, not the maintainer, is responsible for reviewing and merging ready agent pull requests. Cloud sessions also own their toolchain bootstrap: if Rust or required build libraries are absent, the session installs them in the cloud environment using the CI setup as its reference rather than skipping verification or asking the maintainer to intervene. See "Parallel agent coordination and integration" and "Cloud environment bootstrap" above.
- 2026-08-28: Supersedes the 2026-08-27 wave-based work order. `ROADMAP.md` now has only Implemented and Open lists, with Open split into Bugs and Features and each list ordered by criticality. All coding sessions take the first eligible Open Bug, then the first eligible Open Feature, strictly top to bottom. Also authorizes a claimed WIP branch and pull request as the verification transport when a cloud execution sandbox cannot run Rust after genuine bootstrap attempts; required repository CI must be green before merge.
- 2026-09-01: Supersedes the 2026-08-28 pull-request-based coordination policy above. The maintainer, live, asked sessions to stop opening pull requests and push finished, verified work directly to `main` instead. The claim-commit ledger in `ROADMAP.md` remains the coordination mechanism between parallel sessions, and a short-lived `agent/<work-item-slug>` branch may still be pushed transiently to get an independent CI run before the work lands, since `ci.yml` already triggers on any push, not only on pull requests; what changes is that no GitHub pull request needs to be opened, reviewed, or merged through GitHub's UI for that landing to happen. See the updated "Parallel agent coordination and integration" and "Daily automated feature implementation" sections above for the full protocol. Any pull request already open at the time of this change is finished the same way (verified, conflicts resolved against current `main`, pushed directly) rather than merged through GitHub, though using GitHub's own merge button on one of those pre-existing pull requests is not itself a violation of this rule; only opening a new one for new work is.
- 2026-09-01: The maintainer, live, pointed out that `ROADMAP.md` had accumulated checked (`✅`) items still sitting under the Open Bugs or Open Features lists instead of the Implemented section. Every `✅` item must live under `## Implemented`, with no exception; an item is moved there in the same change that marks it done, never left under Open "for now." A session that notices a misplaced `✅` item anywhere else in the file should move it to Implemented on sight, the same way it would fix any other stale roadmap state, whether or not that item is the one it is actively working on.
